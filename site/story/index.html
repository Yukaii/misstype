隨打注音：背後的故事與技術演化

作者：Yukai Huang · 更新：2026 年 10 月 · 技術棧：Zig / WebAssembly / C ABI

這是一個關於「摸黑打字」的妄想、分離式觸控板原型、Jev 模型的啟發，到最終決定親手重寫注音輸入法核心，並將它移植到 Zig 與 WebAssembly 的完整技術歷程。

1. 起源：深夜長途客運上的摸黑打字

這一切的起點，是一次深夜長途客運的旅程。

夜深了，國道客運的車廂熄了頂燈，周圍的乘客大多已經沉沉入睡。窗外是一望無際的黑夜與偶爾掠過的路燈，車內安靜得只剩下引擎的低鳴。在這個時候，腦海裡總會湧現許多想法、待整理的筆記，或是想回覆的訊息。

但我不想、也不能打開頭頂上刺眼的閱讀燈——那樣做既會干擾周圍熟睡的乘客，也會在黑暗中顯得突兀且疲累。然而，如果試著摸黑在筆電或手機上打字，下場通常慘不忍睹：看不見鍵盤的實體鍵帽位置，雙手只要稍微偏離基準鍵，敲出來的全是一堆無法識別的亂碼；在手機螢幕上觸控盲打更是如此，手指只要位移幾公釐，每個字都要狂按退格鍵刪掉重來。

「如果能在完全不開燈、完全不用眼睛看鍵盤的前提下，單純依賴肌肉記憶就能把心裡的想法流暢敲出來，該有多好？」

一個念頭油然而生：最理想的輸入硬體，或許是兩塊小巧的獨立分離式觸控板。雙手各拿一塊，或者自然地搭放在大腿兩側。大腦只需要維持大致的相對方位感，手指憑著肌肉記憶隨意敲擊平面，就能完成輸入。

2. 原型探索：分離式觸控表面與空間不確定性

有了這個想法後，我開始動手製作第一版原型（專案早期的 M0–M2 階段）。

但很快就碰到了核心難題：缺乏實體按鍵邊界時，輸入本質上就是充滿雜訊與不確定性的。

在實體機械鍵盤上，一顆鍵要麼按下了，要麼沒按下；但在平滑的觸控板上，敲擊只是一組連續的 (x, y) 座標。當你憑著肌肉記憶盲打時：

  • 手指可能落在目標按鍵周圍幾公釐的模糊邊界內（鄰近鍵偏移）。
  • 雙手同時敲擊時，左右手的時間戳記經常會有些微顛倒（順序打反 / Transposition）。
  • 有時滑步太快，中間某個音節符號可能漏敲或力道過輕未觸發（漏打符號）。

這意味著，輸入法核心不能再依賴過去那種「精確字碼比對」的死板邏輯。它必須具備機率解碼（Probabilistic Decoding）能力，將帶有空間不確定性、時間抖動的語音信號流，轉化為合理的自然語言句子。

3. 關鍵啟發：Jev 模型與智慧選字浪潮

就在我思索如何構建這個容錯解碼層時，AI 領域迎來了一波輕量化推理模型的革新——特別是 Typesafe AI 發布的 Jev 模型。

Jev 這類專注於極速 token 選擇、結構化約束候選排名的推理架構，帶來了強烈的啟發： 輸入法的候選字消歧與自動重排，不正是小型語言模型與機率格網（Lattice）最天造地設的應用場景嗎？

幾乎在同一時期，社群中一位日本工程師展示了一套創新的輸入法——它利用模型即時偵測輸入脈絡，讓使用者在同一個輸入流中自由混打日文與英文，完全不需要手動按鍵切換模式。

這兩個信號徹底打通了我的思路：幾十年來，我們習以為常的輸入法架構（敲精確按鍵、跳出候選字框、手動逐字翻頁挑選）本質上是 1990 年代計算資源受限下的妥協產物，而不是人類思維的最佳輸入型態。

4. 頓悟與轉向：先解決注音輸入法二十年的痛苦

在做硬體原型的過程中，我突然被一個更根本的問題擊中了：

「我每天在電腦上打幾千幾萬字的繁體中文注音輸入法，體驗明明就這麼痛苦，為什麼我不先親手把軟體輸入法的體驗做好？」

台灣使用者每天使用的注音輸入法，長年存在幾大難以忍受的痛點：

  1. 強制要求敲擊聲調：注音本體集中在鍵盤主打字區，但聲調（ˊ ˇ ˋ ˙）卻被硬生生丟在最上方的數字列或標點區。每敲一個字，手指就得大幅度往上拉扯。如果不敲聲調，傳統輸入法就無法判定音節切換，甚至直接報錯。
  2. 對錯誤零容忍：打字速度一快，兩指順序打反（例如按快把「ㄐㄧㄣ」打成 urp 而非 rup）、手指不小心擦到隔壁鍵、或是少按了一個介音，傳統輸入法會立刻亮起紅字或跳出一堆牛頭不對馬嘴的亂碼，逼得你只能無奈狂按 Backspace 刪掉整串重打。
  3. 思緒被反覆切碎：寫作與思考講求流暢的心流（flow）。但現有輸入法逼你每打兩三個字，就得停下視線去看候選字窗、按方向鍵挑字、按確認鍵。思緒就在一次次的選字中被切得粉碎。

之前的硬體想法至此有了全新的聚焦：何不先為注音使用者打造一個真正順手的現代輸入法？

目標非常明確：不需要打聲調、順序打反能猜到、按到鄰鍵能救回、漏打符號能修復，整句話一口氣打完自然呈現。

說做就做——我放下了硬體外殼的折騰，開始全心撰寫輸入法解碼引擎。第一版原型誕生後，那種「手隨便敲、字自動對」的暢快感，超出了最初的預期。「隨打注音（Misstype）」正式啟程。

5. 技術躍遷：核心徹底重寫為 Zig

最初的解碼概念先在 Python 上驗證，隨後在 macOS 上以 Swift 實作了 MisstypeCore。

Swift 在 macOS 原生環境下表現不錯，但當專案進一步擴展到 Linux（支援 fcitx5 與 IBus 架構）、並追求在不同作業系統間無縫複用時，架構層面的硬傷開始浮現：

  • 執行環境沉重：在 Linux 上執行 Swift 依賴龐大的 Swift runtime，CI 與套件體積動輒以 GB 計算，跨平台編譯極其痛苦。
  • 記憶體配置開銷：輸入法要求每次按鍵都在微秒級別內回應。每次按鍵背後要跑波束搜尋（Beam Search）、晶格生成（Lattice Construction）與字頻加權。Swift 的 ARC 自動引用計數與頻繁的堆積配置在極高頻率下產生了可觀的開銷。

為了達成真正的零依賴、極致效能與跨平台自由，我做了一個關鍵決定：將整個輸入法核心用 Zig 徹底重寫（core-zig/）。

為什麼選擇 Zig？

面向 Swift 原型時代 Zig 核心（現行架構）
C ABI 匯出 需要 @_cdecl 與封裝膠水層 原生支援 C 呼叫約定，直接匯出 misstype.h
跨平台編譯 Linux 需專用 3.7GB Docker 映像檔 單一固定版本編譯器，一鍵跨編譯 x86_64 / aarch64 / wasm
記憶體模型 ARC 引用計數，分散配置與釋放 Arena 配置器：單次解碼全走 Arena，解碼完畢 O(1) 瞬時釋放
解碼延遲 約 1ms ~ 25ms（含排程與物件開銷） 0.1ms ~ 0.5ms（純本地運算，完全感受不到延遲）

重寫後的 Zig 核心帶來了無比純粹的架構：macOS 的輸入法適配器（IMK）與 Linux 的 fcitx5 / IBus 模組，全部直接連結同一個編譯好的共享庫。沒有虛擬機、沒有垃圾回收卡頓、沒有跨平台行為差異。

6. 跨越邊界：WebAssembly 與離線 Markdown 編輯器

當核心完全用無外部相依的 Zig 實作後，一個強大的可能性自然解鎖了：將核心編譯成 WebAssembly（wasm32-wasi）。

這直接解決了一個長年困擾許多使用者的現實限制：

在 iPadOS 等封閉平台上，如果外接實體硬體鍵盤，蘋果作業系統強制限制使用者只能使用官方輸入法，完全無法安裝任何第三方輸入法擴充套件。

但我既然有了能在瀏覽器內高效運行的 WASM 核心，為什麼不直接做一個自帶輸入法的編輯器？

這就是 隨打注音 Markdown 編輯器（PWA）的由來。

  • 瀏覽器原生輸入攔截：編輯器基於 ProseMirror 構建，透過 JavaScript 捕獲實體按鍵事件，直接餵給背景的 misstype.wasm。
  • 離線運行能力：整合 Service Worker 與離線快取，第一次載入後完全不需要網路，即使在無網路的飛機或偏遠旅途中也能穩定寫作。
  • 隨處可用，免安裝：不論是在學校電腦、公司受限的終端機、朋友的筆電，甚至是不給裝輸入法的裝置上，只要打開網頁，立刻擁有完整的隨打注音體驗。

7. 結語：為自己的雙手而造

回頭看這趟旅程，從深夜客運上因為無法開燈而萌生的分離式觸控板奇想，到看見新一代模型時對智慧輸入法的想像，再到決定回歸繁體中文注音輸入的核心痛點；從 Swift 原型、Zig 重寫，一路走到能在瀏覽器隨處運行的 WebAssembly。

隨打注音從一開始就不是為了滿足商業指標而生的產物，而是為了解決自己每天真實遭遇的打字痛苦。它可能還有不完美的地方，字典也還在持續調整，但每一次敲下鍵盤、不用管聲調、就算按錯順序也能瞬間拼出想要的那句話時，那種順暢與自由感，就是這一切折騰最好的回報。
